## Observations requiring explicit triage before UI close-out

Checkpoint 2 surfaced two pre-existing cases beyond the approved IDs-only correction. They remain open observations, not approved additional implementation or accepted deferrals. Checkpoint 5 must obtain an explicit resolution/deferral decision; any scope/count change must be approved first.

- **Event-label inference:** the existing `ObservabilityLogs.tsx` passes audit summary/system event name as `message` to `getActivityTypeLabel`; the shared formatter falls back to Comment for unrecognized text, including `TASK_UPDATED` as a system event name. It does not use the audit `eventType`. Source at `f1a53b0` and the browser fixtures confirm this is pre-existing. Correction requires a separately approved event-label/formatter scope, not permission or API expansion.
- **Narrow project scrolling:** at 320×568, activating Insights can horizontally scroll the project content container and leave the card heading partly outside view. Browser geometry records the same card width/position and container overflow with UUID chips hidden (equivalent to the old missing-field context); this is not a UUID wrapping regression. The project Tabs/container remains separate from the log metadata. Resolve through explicitly agreed responsive scope or accept a recorded deferral before UI closure.

## Scope-change and finish rules

- Work against this numbered list. Any new finding is recorded with evidence and impact before further implementation is proposed.
- Regressions caused by an approved checkpoint are fixed within that checkpoint. A separate pre-existing finding is classified as a release blocker or a proposed deferral, with an explicit scope/count update for approval. Do not silently add another lettered fix batch.
- Close-out verification checks the original module matrix and changed flows: authentication/settings, team selection/navigation/overview/members, projects, task page/dialog/board/list, activity, notifications, users/profiles and insights/logs. Cover desktop/mobile/short layouts, keyboard use, relevant light/dark states, loading/error/empty/pending/retry and archived/denied cases, with valid current API fixtures.
- A passing UI review closes 2J3. Production-readiness sign-off requires checkpoints 6–8 for the agreed environment and usage targets, with limits recorded.
- New Jira capabilities (sprints/backlogs/custom workflows/integrations), archive restoration, public-key enrichment beyond the selected log correction, missing-page redesign, a broad visual redesign and unrelated dependency upgrades are separate scope decisions.
