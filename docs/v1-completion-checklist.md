## Scope-change and finish rules

- Work against this numbered list. Any new finding is recorded with evidence and impact before further implementation is proposed.
- Regressions caused by an approved checkpoint are fixed within that checkpoint. A separate pre-existing finding is classified as a release blocker or a proposed deferral, with an explicit scope/count update for approval. Do not silently add another lettered fix batch.
- Close-out verification checks the original module matrix and changed flows: authentication/settings, team selection/navigation/overview/members, projects, task page/dialog/board/list, activity, notifications, users/profiles and insights/logs. Cover desktop/mobile/short layouts, keyboard use, relevant light/dark states, loading/error/empty/pending/retry and archived/denied cases, with valid current API fixtures.
- A passing UI review closes 2J3. Production-readiness sign-off requires checkpoints 6–8 for the agreed environment and usage targets, with limits recorded.
- New Jira capabilities (sprints/backlogs/custom workflows/integrations), archive restoration, public-key enrichment beyond the selected log correction, missing-page redesign, a broad visual redesign and unrelated dependency upgrades are separate scope decisions.
