# Phase 2H, part 3: browser sessions and reliable feedback

Implemented November 4, 2026 against user commit `71ce11e` (`fix: make user edits atomic and restrict profile visibility`). Approved scope: coordinate refresh across tabs, automatically follow confirmed browser account changes, propagate confirmed logout, and fix remaining loading/save-error/retry states with regressions. The user makes all commits.

## What changes for users

1. **Tabs follow the same browser account.** Confirmed login or registration announces a new session generation. Other tabs immediately clear prior-account queries and memory tokens, gate protected routes, and refresh into the account represented by the browser's HttpOnly cookie. No account identity or bearer token is broadcast or persisted. Confirmed logout and successful self email/password changes sign out the other tabs too.
2. **Concurrent refreshes no longer race cookie rotation.** Same-tab requests still share one refresh promise. Across tabs, a native Web Lock serializes refresh, login, registration, logout, and self credential changes. Each tab's refresh can still make its own HTTP request, using the latest cookie after acquiring the lock; this is serialization, not cross-tab response sharing. A queued operation cannot log out or change credentials for a newer account.
3. **Temporary failures remain retryable.** Refresh network errors and server failures no longer impersonate confirmed session expiration. Bootstrap shows a blocking session error with Retry. Failed logout preserves the local session and offers Retry sign out. A confirmed refresh 401 still clears private state and signs out. Auth HTTP operations use 20-second timeouts so a normal stalled network request does not hold the browser lock indefinitely.
4. **Inline edits retain drafts after failure.** Task/project/team name and description fields await the server, disable duplicate saves and dismissal while pending, preserve failed drafts through background refetches, and show an inline error with Retry save. Descriptions may intentionally be cleared; names remain nonblank. Keyboard activation and input focus are supported. There is no automatic write retry after an uncertain response.
5. **Archive failures stay visible.** Task/project/team confirmation dialogs stay open while pending and after failure, disable cancellation while saving, and navigate/close only after confirmed success. An unconfirmed response says to refresh before retrying rather than claiming nothing changed.
6. **Failed reads do not look like empty data.** Project task lists, task/project/team activity, team overview, and team/project insights show an error with Retry. Overview counts wait for their source queries rather than briefly claiming zero. Project creation errors and project status errors are visible; pending project status changes disable the selector.

The backend authorization matrix, archive semantics, task workflows, notification delivery, and API/schema contracts are unchanged. This phase changes the browser session lifecycle and failure presentation, not module business rules. No application dependency or lockfile changed.

## Session design and limits

`features/auth/utils/sessionCoordinator.ts` supplies one injectable coordinator and the browser singleton. Its API-scoped local-storage entry contains only an opaque random generation and an `active`/`signed-out` flag. Storage notices plus focus/pageshow checks synchronize tabs. Every protected request and successful response also checks shared state, covering missed or delayed notices and rejecting old-account reads before they can populate new-account queries. Existing mutation revision guards continue to prevent delayed/offline writes from being replayed under another account.

The browser must support native [Web Locks](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API), secure contexts (HTTPS in deployment, localhost for development), and site storage. There is deliberately no unlocked cookie-rotation fallback. Unsupported browsers or blocked/malformed session storage receive an actionable session error. Same-origin tabs using the same configured API participate; separate browsers, devices, and frontend origins do not share this lock or marker. The backend's existing revocation checks remain authoritative there.

Storage contains no access/refresh token, user ID, email, or password. Access tokens remain memory-only and refresh credentials remain HttpOnly cookies. The [storage event](https://developer.mozilla.org/en-US/docs/Web/API/Window/storage_event) is a wake-up notice; subscribers reread current durable state rather than trusting an event's older payload. The initiating tab is notified directly.

Self email/password writes hold the cookie/session lock so another login cannot switch their target mid-operation. Those requests suppress automatic interceptor refresh while holding the lock. If a write receives 401, the lock is released before one refresh and one same-session retry; network errors and other statuses are not replayed. Revision and generation checks reject a newer account. After successful credential revocation, cookie cleanup is best effort under the same lock: failed cleanup cannot turn an already completed credential change into a reported write failure. All tabs are signed out and the server already rejects revoked sessions.

If the browser closes or loses a response after the server accepts a request, the client cannot infer its outcome. The existing backend session-family/reuse rules still apply, including fail-closed rotation recovery. This is not a server idempotency protocol or a real-backend end-to-end test suite.
