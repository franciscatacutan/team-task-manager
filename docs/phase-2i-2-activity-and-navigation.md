# Phase 2I, part 2: complete activity search and reliable destinations

Implemented November 4, 2026 against user commit `97af042` (`fix: paginate notifications and synchronize unread state`). Approved scope: full authorized activity search, consistent page grouping/order, public routing contracts, and notification destination handling with regression tests. The user chose current-page grouping in first-event chronology, and unavailable notifications remaining in the inbox after being marked read. The user makes all commits.

## Before and after

Activity search previously filtered only the currently loaded rows. Team/project screens requested 1,000 rows to compensate, while task history fetched ten and never sent search to the backend. Group ordering also interpreted Newest/Oldest as reverse/forward alphabetical order for non-date headings. Distinct people/projects/tasks with the same display name could merge into one group. The activity API returned database IDs but omitted the project keys/task numbers expected by the UI, so task navigation could be unavailable despite a rendered history row.

Search now runs on the server **inside the authorized team/project/task scope, before pagination and count**. All three main history screens request 20 rows per page, use a debounced search, reset to page one on search/order changes, and show matching totals. Groups cover only the displayed page and explicitly say so. Their order follows each group's first event in the selected chronological order; it does not alphabetically reorder people/projects/tasks. Stable identities separate duplicate display names.

Notifications previously navigated using the inbox item's target path after marking read, even when the user had since lost access. Opening an item now marks it read if necessary, then asks an owned-notification endpoint for a fresh authorized destination. Missing or inaccessible destinations show **Destination unavailable**, retain the notification in history, and leave the inbox open. A network/server failure checking a destination is a retryable lookup error, not a declaration that the item is unavailable. Already-read notifications are checked afresh without another read write.

## Search, ordering and pagination

- Existing activity GET routes accept optional `search`: `/api/teams/{teamKey}/activities`, `/api/teams/{teamKey}/projects/{projectKey}/activities`, and `/api/teams/{teamKey}/projects/{projectKey}/tasks/{taskNumber}/activities`. Empty/whitespace search retains the unfiltered history. Names remain `name` throughout task/project contracts.
- Search is case-insensitive after trimming, at most 200 characters, and includes event messages, actor first/last/full name and email, current task/project names, public project keys, task numbers, stored team/project/task/subject-user labels, raw event types and their displayed category labels (for example Archived). Historical labels remain searchable after an item is renamed. `%`, `_`, and backslash are escaped as literal search characters.
- One scoped specification supplies both page results and matching totals. Existing service authorization still runs first. Search does not grant directory/profile access or extend the scope of team/project/task history.
- Supported activity sort fields are `createdAt` and `id`. Default chronological order remains newest first. An ID tie-breaker in the selected timestamp direction makes equal timestamps deterministic. Unsupported/nested sorts and overlong searches receive 400. Existing API default page size remains ten; the three history screens explicitly request twenty. Other consumers, including the five-row team overview, retain their requested sizes.
- Requests include every normalized filter in the shared query key and consume Axios cancellation signals. There is no old-filter/old-workspace placeholder data. Controls remain mounted while loading or after an error, preserving typing/focus and making Retry available. Search/order and workspace changes reset pagination; an out-of-range page recovers to a valid page.
- Group selection is a local presentation choice, not a server group-paging parameter. A group may continue on another page. Grouping uses user/resource IDs, with legacy identifier fallbacks, and preserves first-event insertion order. Search spans full authorized history even though grouping is page-local.

Task-number search uses an actual Hibernate criteria SQL cast. Hibernate's [criteria migration guidance](https://docs.hibernate.org/orm/6.6/migration-guide/#criteria-query) distinguishes `JpaExpression.cast()` from `Expression.as()`, which changes the Java expression type without guaranteeing SQL conversion. PostgreSQL JSONB label extraction uses the existing database stack; no new search dependency is installed.

## Read policy and navigation contracts

`WorkspaceReadPolicy` centralizes the existing detail-read rules and is reused for destinations and history links:

| Viewer                        | Active team/project/task | Archived item or archived parent           |
| ----------------------------- | ------------------------ | ------------------------------------------ |
| Global ADMIN/SUPER_ADMIN      | Readable                 | Readable                                   |
| Current team OWNER/ADMIN      | Readable                 | Readable, with existing read-only behavior |
| Current regular team member   | Readable                 | Direct archived detail remains unavailable |
| Former/unrelated regular user | Unavailable              | Unavailable                                |

The private read validators in TeamService, ProjectService and TaskService now delegate to that policy, preserving existing 404 behavior. Write authorization is unchanged. Global read access does not create team membership or give global admins new editing power. A fresh read-capability snapshot can be reused while mapping one history page; it is not persisted or cached across requests.

The approved history scope is preserved: a regular member may still see historical rows in an accessible active team/project for an archived child, but receives no clickable destination to that child. Authorized owners/team admins/global admins retain archived-task links. Task history itself remains gated by the task's direct-read policy.

Activity responses retain IDs and names and **add** `project.key`, `task.taskNumber`, and nullable `targetPath`. IDs identify records and grouping; public keys/numbers construct routes. These are separate purposes, not replacements or aliases for one another. History text can remain when no destination is available. The frontend now shares the actual activity-record contract, including structured type/details and limited actor identity; it does not assume every project event has a task. Comment-write responses include current task routing fields too.

`GET /api/notifications/{notificationId}/destination` first verifies notification ownership, then returns `{ "available": true, "targetPath": "/teams/..." }` or `{ "available": false, "targetPath": null }`. Unknown and other users' notification IDs return the same 404. Missing targets, lost membership, forbidden archived reads, and inconsistent parent metadata return the same unavailable outcome. The endpoint itself has no read-state side effect.

The resolver uses current database/public identifiers and shared read rules. It supports legacy activity metadata when notification identity columns are absent, preserves membership-event `/members` routes, and never follows an arbitrary stored URL. Unidentifiable legacy paths are unavailable rather than guessed or redirected to a parent. The old inbox `targetPath` field remains for compatibility; the new client does not treat it as an authorization decision or use it for opening notifications.

Opening an unread notification still uses the existing read endpoint and refreshes inbox/counts. Destination failures can be retried by reopening the now-read item, without repeating a confirmed read. Unavailable notifications disappear from the Unread filter after being read but remain under All; the explanation stays visible. Pending read/lookup actions disable competing controls/dismissal. Revision guards prevent a previous account's late result from navigating afterward.

Activity rows use the server-authorized task link; team history/overview navigate to it, and project history keeps its task-modal flow for a permitted task. Rows without a destination are not interactive. Keyboard activation remains supported; keyboard actions on nested Show more/less controls do not accidentally open the task.

Permissions can change after a destination check. The actual detail endpoint always authorizes its request again; a link is not an access grant. No cross-device real-time delivery or permission-change subscription is added.
