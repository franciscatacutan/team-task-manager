# Task-board interaction follow-up: status movement

Prepared November 6, 2026 against user commit `055e0f8`. The user approved status movement first after a read-only interaction review. Team Task Manager remains a task/ticket manager with **Team → Project → Task** organization; this work does not copy Jira's product or introduce its additional features.

This is an approved UI follow-up, not a ninth release checkpoint. Checkpoint 7's physical LAN/hosting acceptance and checkpoint 8's broader release/security/load acceptance remain open. The assistant has not staged, committed or pushed anything.

## What changed and why

1. **Drag changes status, not rank.** The board now uses draggable tasks and droppable status columns. Same-column dragging no longer shifts neighboring cards as if a manual order would be saved. Cards retain the selected server sort; same-column drops explain that the status is unchanged. There is no ranking field, schema migration or optimistic insertion into a guessed position.
2. **Destinations are explicit.** Allowed columns have a check and highlighted border, the hovered allowed target has a ring, and disallowed columns have a barred icon with an error ring when hovered. The current column stays neutral. These cues use the existing transition rules; they grant no new permission. Archived/read-only and terminal tasks remain restricted.
3. **Drop and save are one sequence.** The original card stays faded in its last confirmed position while saving. The solid dragged copy stays at the drop location until the mutation and cache refresh settle, then animates for 160 ms to the actual rendered server-sorted card. If that card is absent from the loaded/filter results, the copy fades in place. Failure settles back toward the confirmed card. It no longer animates back to the source before a successful save. Matching grip spacing keeps overlay/card dimensions consistent.
4. **Feedback no longer moves the board.** Saving uses a fixed, named status message and destination spinner instead of inserting a paragraph above the tabs. Handles stay locked until settlement. Errors remain visible with Retry/Dismiss; success and same-column information clear after 3.5 seconds. Retry reads the latest task first: if the intended status already exists after a lost response, it confirms that state without a duplicate PATCH; otherwise the server validates the retry normally. A concurrent change may still be rejected by the existing workflow/authorization rules. No API idempotency contract was added.
5. **Keyboard movement follows columns.** Space picks up/drops, Left/Right choose allowed displayed status columns, and Escape cancels. Keys do not select incidental cards inside a populated column. Screen-reader instructions and announcements identify the task/status and distinguish a requested move from confirmation. After keyboard settlement, focus follows the enabled handle or the task opener for a terminal destination, unless the user has focused another control. Project/account changes reset the drag context; late completions cannot restore stale feedback or focus.
6. **Reduced motion is live.** The browser's preference disables decorative drop/hover motion and spinner rotation. Changing the preference cancels an active settling animation. Missing motion APIs use static feedback. This is limited to task movement and its feedback; it is not a claim that every application animation was audited or changed.

## Approved whole-card mouse follow-up

After trying the board, the user explicitly selected **whole-card mouse/trackpad dragging with grip-only touch/keyboard dragging** on November 6, 2026. `DraggableTaskCard.tsx` now forwards mouse pointer-down events from the card body and task-name button to the existing sensor. The same 6 px activation threshold distinguishes a click/small movement from a drag. A completed drag suppresses the incidental click; a normal name click or keyboard activation still opens details. The body displays a grab cursor only when movement is enabled.

Touch pointer-down on the body is left to the browser for native scrolling; only the grip retains `touch-none` and its pointer/keyboard listeners. Other interactive controls do not start a body drag, and grip events are not forwarded twice. Read-only/permission/pending guards, right-button rejection, selected server sort, status rules, save/retry handling and reduced-motion behavior are preserved. Clicking the non-name body does not acquire a new open-details behavior.

Follow-up verification: **572 frontend tests in 58 files**, including 12 new pointer/control regressions; strict lint, TypeScript/production compilation and formatting pass. Headless Edge used the actual card components in a disposable Vite fixture with no application API/database access. It verified body/name mouse drops, ordinary and small-movement name clicks, disabled movement, separate keyboard controls, touch-body native scrolling, grip touch pickup/cancel and name tapping. The fixture constrains horizontal board overflow to match application containment; an initial unconstrained fixture distorted mobile viewport geometry and was corrected without changing product layout. This is bounded input testing, not a new full release certification. The earlier real-backend save/retry results remain prior evidence; no backend source, dependency or data changed in this follow-up.

The controlling changes are in `DraggableTaskCard.tsx`, with regressions in `DraggableTaskCard.test.tsx`. To adjust pickup distance, use the existing PointerSensor activation constraint in `TaskBoard.tsx`. Keep the touch/keyboard grip independent when changing pointer routing. No staging, commit or push was performed. Suggested user commit for this follow-up: `fix: restore whole-card mouse dragging`.

## Verification

- Frontend: **560 tests in 57 files**, strict ESLint, TypeScript/production compilation, Prettier and frontend Docker image build. The existing large JavaScript chunk warning remains; bundle splitting is outside this movement batch. No Java/schema source changed; Maven was not rerun for this frontend-only change.
- Regression tests cover deferred confirmation/animation geometry, one in-flight attempt, failed retry, same/invalid column drops, missing rendered destinations, late project/account/unmount settlement, live reduced-motion cancellation, retry GET/PATCH behavior and session changes. Existing archive, permission, pagination, cache and keyboard tests remain; keyboard coverage now includes populated destinations.
- A real isolated PostgreSQL 17/backend stack with generated accounts, two teams, three projects and 18 tasks exercised desktop pointer, populated-column keyboard, cancellation, terminal focus, selected Name-ascending sorting, dark-mode cues/errors and touch pickup/cancel. This used localhost only and did not modify the existing database or install trust certificates.
- Controlled 1.2-second real PATCH delay: overlay stayed at the destination while pending; at 1440×1000, board top stayed **556 px** and height **412 px** before/during save. Same-column neighbors had no transforms and no PATCH. A one-time 503 retained a useful error and Retry issued GET then one PATCH. A real accepted write followed by a simulated lost response was recovered with no duplicate PATCH. Reduced-motion mode created no decorative Web Animation and no hover translation. Invalid drops made no write; navigating away during a real pending save produced no stale feedback on the next page.
- The compiled production frontend was also smoke-tested against that isolated backend through the same-origin nginx proxy. These bounded checks are not checkpoint 8 release acceptance, an iOS/Safari certification, physical-device LAN verification or a broad accessibility certification.

Browser screenshots, sanitized request observations and recordings are retained in the local interaction-review artifacts, outside Git. Credentials, cookie storage and disposable database files are not included. Early diagnostic screenshots are distinguished from final dark-mode evidence; a transient dialog entrance frame and two harness fixture/color-format assumptions were not application defects.

## Findings awaiting the user's next choice

The wider audit also found opportunities in project/header and card density (especially on mobile), lost list/search context when returning from a full task page, and a System-theme preference that does not follow OS changes until reload. Card-body opening, overdue emphasis, creation defaults and semantic badge styling are additional design options, not changes approved in this batch. They require their own bounded scope/behavior choices before implementation. The original checkpoint 5 completion covered its agreed inventory, not every future interaction/design improvement.

When reviewing this batch, try a slow save, a same-column drop, a failed save with Retry, keyboard movement into a populated column, and your operating system's reduced-motion setting. Suggested user commit after review: `fix: polish task board status movement and feedback`.
